# Tentukan cermin status website di Status Channel

Parent: [Cermin status website di Status Channel SO pickup Internal](../map.md)
Type: grilling
Status: owner decisions confirmed; accounting residual risk accepted; updated spec Ready and local build tickets published (no implementation permission)
Blocked by: none (01–02 answered); Ready/publication approvals still separate

## Intent and evidence

The owner wants **a nice-to-have display-only mirror** of website progress in Jubelio's **Status Channel**, not a Jubelio payment/WMS authority and never a condition for local checkout, payment, or pickup. [Issue 02](02-pastikan-asal-status-ui-dan-transisi-pickup.md) confirms in the vendor UI that the INTERNAL test SO 68397 displays a create-time `channel_status` marker, whereas control 68396 is blank; both show `UNKNOWN` in the distinct **Status Jubelio** column. This proves only that create-time custom values render in this test account, not that editing an invoiced SO is safe or that Jubelio has no downstream behavior for arbitrary channel values.

## Owner-confirmed behavior

| Local state/event | Proposed `channel_status` mirror | Boundary |
|---|---|---|
| New SO create request (`source=1`) | **Belum Bayar** in the SAME `POST /sales/orders/` payload | One create request, not a follow-up status call. If the POST response is lost, marker may exist remotely while local create remains ambiguous; the durable local operation ledger still governs confirmation. Current production builder omits this field; the standalone probe supplied it only in a test payload. |
| Midtrans authoritatively `paid`, and Jubelio settlement results in `manual_review` or explicit operator-investigation block | **Menunggu Verifikasi** | Owner clarified: **not** for brief `in_flight`/`pending` verification; fast success skips this update. No second customer payment. The admin review queue may also show paid-but-blocked `processing` orders that are not yet `manual_review`; queue membership alone is not the trigger. |
| Jubelio invoice/payment independently verified **and** local order becomes `ready_for_pickup` | **Siap Proses** | Describes website readiness in Status Channel, **not** `wms_status`, `is_paid`, or a new authority for pickup. |
| Local order becomes `failed_payment` | **Gagal Bayar** | After the terminal local transition, not after one nonterminal Midtrans deny/cancel attempt. If the SO cancel path has started or confirmed, skip the channel edit and persist a mismatch + structured log; the marker may stay stale. Never delay cancel/stock release for the display-only marker. |
| Local order becomes `cancelled` | **Dibatalkan** | The schema permits `cancelled`, but no current runtime path writes it; do not invent a cancellation flow. |
| Local order becomes `completed` after verified pickup | **Selesai** | After the local transition, not at Midtrans payment. |

For example, an ambiguous invoice/payment POST is triaged for manual review without repeating the write; an in-flight verification with a known ID may instead reconcile by GET/sweep and never need operator action. These are distinct despite both temporarily preventing pickup ([settlement pipeline](../../../apps/store/src/lib/jubelio-sales-settlement.ts), [lifecycle](../../../apps/store/src/lib/jubelio-sales-lifecycle.ts)).

The intended mirror is **best effort after create**: if a later channel-status edit fails or is ambiguous, local payment/pickup continue under their independent rules. The owner explicitly reaffirmed the initial two-call sequence: one indispensable SO-create POST **with** `Belum Bayar` in its payload, then one independent SO GET to verify identity, branch, items and money before Midtrans ([gateway](../../../apps/store/src/lib/jubelio-sales-client.ts), [checkout](../../../apps/store/src/app/api/checkout/place-order/route.ts)). There is **no third/edit call for the initial marker**. The owner accepts the conditional dependency: rejection, ambiguity or mismatch of the combined SO-create request still blocks checkout under existing safety rules; never blindly re-POST create without the marker. Do not promise that the initial marker is strictly non-blocking. Record the mismatch for investigation; GET-reconcile when safe, never blind-repeat an ambiguous write. A SO that does not exist cannot have a 'not created' channel marker. The `OKCIR_TEST_CREATED` value was test-only, not one of the chosen production labels.

## Remaining evidence and approval gate

The create-time field and **one** post-payment edit were tested, but every later stage would require a separate SO-edit request. The [one-shot experiment](../edit-channel-status-results-2026-09-26.md) created test SO 68398 → invoice 45944 → payment 26, edited `channel_status` once from `Belum Bayar` to `Siap Proses`, and verified GET detail/list and vendor UI. Observed SO/item/totals/stock and the **known** invoice/payment association did not change; **Status Jubelio** remained `UNKNOWN`. This is account-scoped evidence, not a promise for every label, concurrency pattern, or invoiced order. The payments-list q-filter returned zero despite a verified payment, so it cannot rule out hidden accounting effects. A later [one-shot test on SO 68399](../accounting-one-shot-results.md) found two fixture-linked journals from invoice/payment as a positive control; a subsequent single channel edit changed neither the recent journal count/newest ID nor those journal lines or the known SO/invoice/payment fields. The owner reviewed the limits (one fixture, recent page, short delay, no post-edit stock read or vendor CAS guarantee) and **accepted residual accounting risk as no longer blocking Ready review**. This is a risk decision, not proof that every invoiced SO edit is financially inert; implementation/rollout still need separate approval.

The remaining engineering contract must cover persisted per-transition intent/version, at-most-once dispatch, GET confirmation, crash/sweep recovery, ordering when webhook and sweep race, and how a failed display-only mirror is recorded for investigation **without blocking the local order**. The existing [admin review queue](../../../apps/admin/src/app/api/admin/reviews/sales-operations/route.ts) is read-only and currently lists SO/invoice/payment operations and paid-but-blocked orders—not mirror-only mismatches; the owner chose **durable mismatch records plus structured logs** for mirror failures, without adding an admin-review UI in this scope. Discoverability/reconciliation remains an engineering acceptance criterion. `cancelled` has no current runtime writer, so its label is future-facing only. The owner further confirmed that editing a possibly/already canceled SO is not required for Gagal Bayar: skip and record a durable mismatch, rather than preempting the cancel with a marker edit. No more provider writes are authorized by either consumed one-shot approval; no automatic `set-as-paid`/WMS fallback.

**Approval record:** the owner confirmed the status table and best-effort rule, accepted the residual accounting risk after the journal probe, then clarified that Gagal Bayar edits are skipped with a durable mismatch once SO cancel starts. The owner subsequently approved the [updated full spec](../spec-draft.md) as Ready and requested [local build tickets](../build-tickets/). Neither approval grants a new provider POST, automatic implementation, commit, or deployment.
