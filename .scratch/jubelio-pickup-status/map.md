# Cermin status website di Status Channel SO pickup Internal

Label: wayfinder:map

## Destination

[Spesifikasi Ready](spec-draft.md) yang disetujui pemilik untuk mencerminkan **kemajuan order website** pada `channel_status` SO `INTERNAL` pickup yang tampil di kolom **Status Channel** Jubelio. Nilai pilihan pemilik: **Belum Bayar** dikirim di payload create SO yang sama; **Menunggu Verifikasi** hanya saat Midtrans paid dan settlement Jubelio menghasilkan `manual_review`/blokir yang memerlukan pemeriksaan operator (bukan `in_flight` singkat); **Siap Proses** setelah invoice/payment Jubelio terverifikasi dan lokal `ready_for_pickup`; **Gagal Bayar**, **Dibatalkan**, **Selesai** pada status lokal akhir masing-masing. Tujuannya hanya informasi operasional (*nice to have*), bukan status bisnis/pembayaran baru di Jubelio, bukan perubahan **Status Jubelio**/`wms_status`, dan bukan syarat pickup. Semua perubahan setelah create memerlukan edit SO terpisah; [uji jurnal lanjutan](accounting-one-shot-results.md) tidak menemukan perubahan jurnal terkait pada satu fixture. Pemilik menerima risiko residual dan menetapkan akuntansi bukan lagi blocker peninjauan Ready, tanpa mengklaim keamanan finansial universal. SO yang belum ada tidak dapat menyimpan marker. Spesifikasi mendefinisikan perilaku yang dapat diverifikasi, bukan izin untuk mengimplementasikannya.

## Notes

- Sumber awal: [Riset Status Jubelio UNKNOWN](../../plan/research/jubelio-wms-status-unknown.md), [alur Sales Orders saat ini](../../docs/features/jubelio-sales-orders.md). Lihat juga [aturan pengembangan](../../.agents/skills/development-workflow/SKILL.md), serta skill `grilling` dan `domain-modeling` untuk tiket keputusan.
- Pisahkan **Status Channel** (`channel_status`) dari **Status Jubelio** (`wms_status`), `is_paid`, serta status pembayaran/fulfillment lokal. Walau nanti cermin memuat tahap pembayaran website, nilai channel bukan bukti `is_paid` Jubelio, WMS siap memproses, atau izin fulfillment lokal. Mekanisme `set-as-paid` dan transisi WMS tidak diteliti lebih lanjut pada jalur aktif ini.
- GET read-only ke akun Jubelio boleh dijalankan saat riset tanpa keputusan tambahan dari pemilik, lewat akses aman dengan redaksi/allowlist tanpa PII. POST apa pun (termasuk `POST /login` untuk memperoleh token) atau operasi yang mengubah data Jubelio membutuhkan izin eksplisit pemilik untuk tindakan/cakupan tersebut; POST tidak dilarang secara mutlak. Peta ini bukan izin uji write, mengubah SO lama, akses SSH/remote, subagen, commit, atau deployment; minta izin terpisah sesuai tindakan yang relevan.
- Pertahankan kebijakan pickup lokal saat ini: invoice/payment yang terverifikasi dapat membuka pickup meskipun label UI Jubelio belum cocok; ketidaksesuaian vendor diselidiki, tidak disamakan dengan gagalnya pembayaran lokal.
- Peta keputusan ini di `.scratch/` dan bukan status plan `plan/index.md`. Spesifikasi Ready dan [enam tiket build lokal](build-tickets/) telah disetujui/diterbitkan secara terpisah; implementasi, POST Jubelio, commit dan deployment tetap butuh izin tersendiri.

Screenshot membuktikan contoh ini, bukan jaminan semua nilai/efek vendor.
- Pemilik mengklarifikasi tujuan: `channel_status` hanya cermin website di Jubelio (*nice to have*), bukan otoritas pembayaran, WMS, atau pickup. [03](issues/03-pilih-alur-status-resmi.md) sudah menyepakati label/trigger: Belum Bayar pada create; Menunggu Verifikasi **hanya bila settlement masuk manual review**, bukan setiap `in_flight`/paid cepat; Siap Proses setelah invoice/payment dan pickup siap; Gagal Bayar/Dibatalkan/Selesai pada hasil akhir. Pemilik secara eksplisit mengonfirmasi tabel perilaku dan aturan best-effort ini; [uji edit sekali pada SO baru 68398](edit-channel-status-results-2026-09-26.md) menunjukkan update `Belum Bayar` → `Siap Proses` di GET tanpa perubahan yang teramati pada SO/stock/asosiasi invoice-payment yang diketahui. Screenshot UI dari pemilik mengonfirmasi SO-000068398 menampilkan **Siap Proses** di Status Channel sementara Status Jubelio tetap `UNKNOWN`; uji jurnal berikutnya pada SO 68399 tidak menemukan perubahan pada jurnal terkait yang diperiksa. Pemilik menerima batas bukti dan menetapkan akuntansi bukan lagi blocker; keputusan ini bukan izin implementasi/rollout. Persetujuan Ready atas spesifikasi lengkap yang direvisi dan penerbitan tiket lokal sudah diberikan kemudian; belum ada implementasi. [04](issues/04-wms-ditunda.md) tetap ditunda, bukan blocker.
- Semua persetujuan POST sebelumnya hanya berlaku untuk uji satu kali yang sudah selesai; tidak ada izin tulis berkelanjutan. Jangan mengulangi percobaan ambigu pada SO 68395 atau mengubah SO uji 68398/68399 tanpa izin baru.

## Settled boundaries and remaining technical proof

- **Siap Proses** dipicu sesudah invoice/payment Jubelio terverifikasi **dan** status lokal `ready_for_pickup`, bukan saat Midtrans `paid` tetapi pickup masih diblokir ([alur](../../docs/features/jubelio-sales-orders.md)). Satu edit awal berhasil di akun uji dan UI; uji jurnal berikutnya tidak menemukan perubahan finansial yang teramati pada fixture berbayar, tetapi tidak menjamin semua kasus. Pemilik menerima risiko residual sebagai non-blocker Ready; SO edit memakai payload penuh ([kontrak](../../docs/jubelio-api/dist.yaml)).
- **Belum Bayar** dipilih sebagai satu field pada POST create SO yang sama, bukan API call edit tambahan. Pada kode saat ini payload builder belum menyertakannya ([kode](../../apps/store/src/lib/jubelio-sales-client.ts)); uji standalone membuktikan Jubelio menerima field itu. **Pemilik menegaskan alur awal dua panggilan Jubelio:** satu POST create SO **dengan** marker, lalu satu GET independen untuk memverifikasi ID, lokasi, item, jumlah/harga/total sebelum Midtrans ([gateway](../../apps/store/src/lib/jubelio-sales-client.ts), [checkout](../../apps/store/src/app/api/checkout/place-order/route.ts)). Tidak ada edit SO ketiga untuk marker awal. Konsekuensi yang diterima: bila POST create gabungan ditolak/ambigu atau GET mismatch, checkout tetap tertahan sesuai pengaman SO saat ini; create tidak boleh diulang buta. Jaminan best-effort/tidak menghambat berlaku bagi **edit cermin setelah create**, bukan request create wajib. Jika respons create hilang, marker bisa ada di Jubelio walau aplikasi belum dapat mengonfirmasi; ledger lokal tetap otoritatif. SO yang belum ada tak dapat menampilkan 'belum terbentuk'.
- Label akhir sudah dipilih: `failed_payment` → **Gagal Bayar**, `cancelled` → **Dibatalkan**, `completed` → **Selesai**. Pemicu hanya sesudah status lokal benar-benar berubah; `cancelled` ada di schema namun belum memiliki jalur runtime aktif ([schema](../../packages/db/src/schema/orders.ts)). **Klarifikasi pemilik untuk gagal bayar:** jika cancel SO telah dimulai/terkonfirmasi, lewati edit channel pada SO itu dan simpan mismatch persisten + log; marker Jubelio boleh tertinggal. Jangan mendahulukan marker dari cancel atau membahayakan pelepasan stok. Tidak ada perubahan jalur pembatalan dalam cakupan ini.
- **Menunggu Verifikasi** hanya ketika settlement invoice/payment Jubelio menghasilkan `manual_review` atau blokir eksplisit untuk investigasi operator; `in_flight`/`pending` singkat tidak memicu label ini. Jalur sukses cepat langsung dari Belum Bayar ke Siap Proses. Antrean review admin juga dapat menampilkan paid-but-blocked yang masih `processing`, tetapi itu tidak otomatis berarti operasi sudah `manual_review` ([kode](../../apps/admin/src/app/api/admin/reviews/sales-operations/route.ts)). Jika cermin gagal/ambigu, jangan blokir proses lokal; catat untuk investigasi dan lakukan GET rekonsiliasi bila aman, tanpa POST ulang buta. Pemilihan seam teknis dan recovery persisten perlu dibuktikan pada rancangan.
- **Visibilitas kegagalan cermin:** pemilik memilih **catatan persisten + log terstruktur**, tanpa perluasan antrean UI admin sekarang. Antrean yang ada hanya memuat operasi sales dan paid-but-blocked, bukan mismatch channel yang berdiri sendiri ([route](../../apps/admin/src/app/api/admin/reviews/sales-operations/route.ts)). Rancangan teknis perlu memastikan catatan dapat ditemukan/direkonsiliasi tanpa menambahkan hak pickup atau retry buta.
- **Bukti akuntansi dan risiko residual:** [uji awal](edit-channel-status-results-2026-09-26.md) membuktikan marker ter-update pada SO ber-invoice/payment tanpa perubahan yang teramati pada SO, stok atau payment yang diketahui, dan screenshot pemilik mengonfirmasi kolom UI pada SO 68398. Filter `q` payment lama tidak dapat membuktikan ketiadaan payment lain. [Uji lanjutan](accounting-one-shot-results.md) pada SO 68399 menemukan dua jurnal baru dari invoice/payment sebagai positive control; sebelum vs sesudah satu edit, total dan ID jurnal terbaru serta detail dua jurnal terkait tetap sama, demikian juga SO/invoice/payment yang diperiksa. Hanya satu fixture, halaman jurnal terbaru dan jeda singkat; tidak ada pengukuran stok pasca-edit atau garansi atas posting tertunda/edit vendor konkuren. **Pemilik menerima risiko residual; akuntansi bukan blocker lagi untuk peninjauan Ready**, bukan klaim edit aman secara universal. Hasil ambigu, recovery persisten, concurrency lokal, dan tes aplikasi tetap perlu dirancang/diuji; semua izin POST uji habis. Nilai `OKCIR_TEST_CREATED` hanya data uji.

## Out of scope

- Target lama agar kolom **Status Jubelio** menampilkan **Belum Dibayar → Siap Proses**, termasuk `set-as-paid`, penyiapan fixture WMS, dan `POST /wms/sales/ready-to-process` — ditunda di [04](issues/04-wms-ditunda.md), bukan alternatif diam-diam untuk jalur channel.
- Mengubah SO lama atau SO uji 68394–68399; semua POST baru dan cleanup butuh rancangan/izin terpisah. Dua SO uji 68396/68397 masih menahan dua unit stok pada akun tersebut ([laporan](combined-test-results-2026-09-26.md)).
- Alur delivery/jenis fulfillment selain checkout pickup saat ini; mengubah UI admin marketplace.
- Implementasi aplikasi, migrasi data, POST ke Jubelio, rollout/deployment, dan mengubah aturan pickup lokal sebagai bagian dari wayfinding ini.
