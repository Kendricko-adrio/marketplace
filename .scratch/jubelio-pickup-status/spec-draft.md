## Problem Statement

Operator yang melihat Sales Order (SO) pickup website berjenis `INTERNAL` di Jubelio tidak bisa membaca kemajuan website dari kolom **Status Channel**. Kolom **Status Jubelio** yang terpisah tetap `UNKNOWN` pada contoh akun yang diperiksa. Operator memerlukan petunjuk tampilan yang konsisten tentang status lokal, tanpa menjadikan Jubelio sumber keputusan baru tentang pembayaran, kesiapan pickup, atau fulfillment.

## Solution

Cerminkan status order website ke `channel_status` SO `INTERNAL` pickup. Marker awal **Belum Bayar** disertakan dalam **POST create SO yang sudah wajib**, kemudian GET independen tetap memverifikasi identitas, cabang, item, kuantitas, harga, dan total sebelum Midtrans. Setelah create terkonfirmasi, edit SO untuk tahap yang relevan bersifat **best effort** dengan intent tercatat, paling banyak satu dispatch per intent, pembacaan balik, serta catatan mismatch persisten dan log terstruktur. Gangguan pada cermin setelah create tidak menghentikan alur pembayaran atau pickup lokal; status lokal dan verifikasi invoice/payment tetap berwenang. Tidak ada penulisan `wms_status`/`is_paid`, `set-as-paid`, atau perubahan aturan pickup.

| Peristiwa yang sudah terjadi secara lokal | Nilai Status Channel | Ketentuan |
|---|---|---|
| Create SO baru | **Belum Bayar** | Dalam POST create yang sama; tidak ada edit ketiga untuk marker awal. SO yang belum ada tidak dapat diberi marker. |
| Midtrans sah `paid` dan settlement masuk `manual_review`/blokir eksplisit yang perlu investigasi operator | **Menunggu Verifikasi** | Bukan ketika `in_flight`/`pending` singkat; keanggotaan antrean admin sendiri bukan bukti trigger. |
| Invoice **dan** payment Jubelio diverifikasi dan order lokal benar-benar `ready_for_pickup` | **Siap Proses** | Bukan ketika baru dibayar di Midtrans; keberhasilan cepat dapat langsung melewati Menunggu Verifikasi. |
| Order lokal benar-benar `failed_payment` | **Gagal Bayar** | Bukan akibat satu percobaan bayar nonterminal. Jika SO belum terkonfirmasi atau pembatalan SO sudah dimulai/terkonfirmasi, **jangan edit**; catat mismatch persisten, sehingga Status Channel mungkin tetap Belum Bayar. |
| Order lokal benar-benar `cancelled` | **Dibatalkan** | Kontrak masa depan saja: saat ini tidak ada jalur runtime aktif yang menulis status ini. |
| Order lokal benar-benar `completed` setelah pickup | **Selesai** | Tidak dipicu oleh pembayaran saja. |

## User Stories

1. Sebagai operator, saya ingin melihat **Belum Bayar** di Status Channel SO pickup baru, sehingga dapat mengenali tahap awal website.
2. Sebagai pelanggan, saya ingin checkout tetap menunggu GET konfirmasi SO yang valid sebelum Midtrans, sehingga marker baru tidak melemahkan pengaman stok dan uang.
3. Sebagai operator, saya ingin melihat **Menunggu Verifikasi** hanya pada pembayaran sah yang terblokir untuk pemeriksaan manusia, sehingga verifikasi singkat tidak tampak seperti insiden.
4. Sebagai operator, saya ingin melihat **Siap Proses** setelah invoice/payment terverifikasi dan pickup lokal siap, sehingga label itu tidak mendahului kelayakan pickup.
5. Sebagai operator, saya ingin melihat **Gagal Bayar** bila order sungguh gagal dan SO masih aman diedit; bila pembatalan SO sudah dimulai, saya ingin mismatch tercatat alih-alih edit berisiko pada SO canceled.
6. Sebagai operator, saya ingin melihat **Dibatalkan** bila suatu saat order lokal benar-benar dibatalkan, tanpa fitur pembatalan baru sekarang.
7. Sebagai operator, saya ingin melihat **Selesai** setelah pickup selesai, sehingga status website yang final terlihat di SO.
8. Sebagai petugas pickup, saya ingin status/izin pickup tetap ditentukan oleh verifikasi settlement dan status lokal, bukan Status Channel, sehingga keterlambatan cermin tidak menolak pickup yang sah.
9. Sebagai operator, saya ingin kegagalan dan hasil edit yang tidak pasti tercatat secara tahan crash dan dapat dicari berdasarkan order/SO, sehingga bisa melakukan investigasi lewat GET yang aman tanpa menulis ulang secara buta.
10. Sebagai operator, saya ingin status terbaru tidak ditimpa oleh hasil lama ketika webhook dan sweep beradu, sehingga Status Channel tidak mundur secara keliru.
11. Sebagai operator, saya ingin bila payment datang terlambat setelah order gagal, cermin mengikuti keadaan lokal terbaru yang sah dan tidak menyamarkan kasus yang tetap diblokir, sehingga label akhir yang basi tidak menjadi otoritas.
12. Sebagai pengelola sistem, saya ingin hasil uji jurnal dan risiko residual yang diterima pemilik tercatat, sehingga keputusan rollout tidak menyamakan tidak ditemukannya perubahan pada satu fixture dengan jaminan aman secara finansial untuk semua SO.

## Implementation Decisions — kontrak yang disetujui; detail internal diuji pada seam yang disepakati

1. **Bahasa domain dan otoritas.** `channel_status` adalah proyeksi informasi website pada kolom Status Channel; `wms_status` adalah Status Jubelio yang lain. Pembayaran Midtrans lokal, invoice/payment Jubelio yang terverifikasi, dan aturan pickup tetap terpisah. Tidak mengisi `is_paid` sebagai jalan pintas.
2. **Create tetap dua langkah provider.** Simpan intent create dengan marker **Belum Bayar** sebelum satu POST create; sesudah respons, satu GET independen untuk identitas/cabang/item/uang sebelum memulai Midtrans. Rejection/ambiguity/mismatch atribut **inti SO** menahan checkout seperti sekarang, tanpa create ulang buta. Jika respons hilang, marker mungkin sudah ada di Jubelio; ledger lokal menentukan status konfirmasi. **Keputusan pemilik:** jika hanya marker pada GET yang berbeda sementara atribut inti SO cocok, checkout boleh lanjut ke Midtrans; simpan mismatch untuk investigasi dan jangan edit/POST ulang secara buta. Marker bukan gate pembayaran baru.
3. **Tahap pasca-create disimpulkan dari keadaan yang sudah terkomit.** Bentuk intent saat transisi lokal sukses, bukan dari callback mentah atau sebelum transaksi status lokal commit. Transisi `failed_payment` akibat create ditolak/tidak ada SO tidak menghasilkan edit. **Keputusan pemilik:** begitu jalur cancel SO dimulai (termasuk intent mungkin-terkirim) atau cancel terkonfirmasi, jangan dispatch edit Gagal Bayar, termasuk intent cermin yang masih menunggu; simpan mismatch persisten + log. Jangan menggeser edit sebelum cancel atau menghambat pembatalan/pelepasan stok demi cermin. Jika SO masih aktif dan jalur cancel tidak dimulai, edit tetap tunduk pada pemeriksaan fail-closed biasa. `manual_review` settlement atau blokir investigasi eksplisit pada paid-but-blocked boleh menjadi Menunggu Verifikasi; `pending`/`in_flight` biasa tidak. Bila pemeriksaan kemudian beres dan lokal `ready_for_pickup`, naik ke Siap Proses. Penyelesaian pickup dapat berasal dari store melalui panggilan admin; cermin harus mengikuti status order store yang telah commit, termasuk jika respons HTTP ke admin hilang.
4. **Intent cermin terpisah dan tahan crash (usulan).** Ledger operasi sales sekarang hanya menerima `create | cancel | invoice | payment` dan unik per `(order, type)`; tidak tepat untuk serangkaian edit channel. Tambahkan penyimpanan persisten khusus proyeksi per order, dengan target tahap/versi monoton, SO ID, nilai yang diinginkan, observasi terakhir, status dispatch (`pending`, `possibly_sent`, `confirmed`, `needs_investigation` atau setara), cap waktu, dan alasan yang aman dari PII. Skema milik paket DB; sesuaikan seeder. Sediakan pencarian operasional terdokumentasi atas order/SO dan status investigasi (misalnya query DB/runbook internal), **tanpa UI atau antrean admin baru**. Jangan menaruh kegagalan cermin pada `fulfillment_blocked_reason`.
5. **Urutan dan izin dispatch (usulan).** Proyeksikan dari status lokal terkini sebelum memutuskan intent; serialisasikan per SO lewat klaim atomik agar webhook, sweep, dan completion tidak mengirim dua edit bersamaan. Rekam intent sebelum POST; satu klaim memberi izin paling banyak satu POST untuk satu target/versi. Jangan kirim target lebih baru ketika edit sebelumnya masih `possibly_sent` dan belum direkonsiliasi. Hasil lama tidak boleh menimpa target yang lebih baru. Jika order berubah dari `failed_payment` menjadi paid lagi (late settlement), nilai Gagal Bayar bukan keadaan akhir yang permanen. Jika intent lama telah terkonfirmasi dan status lokal berubah, buat target baru secara berurutan; jangan mengubah intent yang mungkin sudah dikirim untuk memperoleh izin POST kedua. Tidak menjanjikan compare-and-swap di vendor yang belum dibuktikan.
6. **Edit full-payload, bukan PATCH (usulan fail-closed).** Sebelum satu POST edit, baca SO terkini dan cocokkan identitas/source/lokasi, status cancel, invoice link, ID baris detail, item/kuantitas/harga/total, serta data yang wajib dipertahankan. Bangun payload allowlist edit dari sumber terverifikasi ditambah field wajib yang benar; pertahankan ID SO, nomor SO dan ID detail, bukan `[auto]`/0. Satu-satunya perubahan yang dimaksud adalah `channel_status`. Jika shape tidak cukup, SO telah berubah, atau edit berisiko menulis ulang atribut finansial/item, **jangan edit**; simpan investigasi. Tidak menyalin mentah GET ke POST, tidak memalsukan `is_paid`, tidak menambah WMS/penanda akuntansi. Perubahan vendor oleh pihak luar di antara GET dan POST tidak dilindungi CAS; risiko residual ini diterima pemilik untuk melanjutkan peninjauan Ready, sementara pengaman fail-closed dan tes race lokal tetap wajib pada implementasi.
7. **GET dan hasil ambigu (usulan).** Setelah satu edit, konfirmasi `channel_status` dan atribut inti melalui GET SO; konfirmasi hasil yang cocok, catat mismatch/unknown untuk investigasi. Timeout, 5xx, respons rusak, atau crash sesudah klaim berarti *mungkin terkirim*: sweep hanya melakukan GET dengan SO ID yang tersimpan, **tidak** mengulangi POST. GET yang gagal/berbeda dari target bukan alasan melakukan POST ulang. Hanya intent yang belum pernah diklaim dapat mendapat satu kesempatan dispatch saat pemulihan; keputusan lanjut ke target terbaru mensyaratkan keadaan lama terkonfirmasi atau tindakan operator eksplisit bila ambigu. Kegagalan cermin dicatat persisten + log terstruktur tanpa data pelanggan/raw response.
8. **Tempat pemulihan (usulan).** Rekonsiliasi terjadwal memindai catatan cermin yang belum selesai secara terbatas, termasuk order yang sudah `ready_for_pickup`, `failed_payment`, atau `completed`; jangan mengandalkan sweep settlement yang hanya memilih `processing + paid`. Jangan membuat proses pickup atau respons webhook bergantung pada keberhasilan cermin pasca-create. Contoh: payment GET sudah cocok, status lokal berubah ke `ready_for_pickup`, tetapi edit Siap Proses timeout — pickup code tetap berlaku; catatan `possibly_sent` dibaca ulang dari SO ID, tanpa POST ulang.
9. **Bukti dan keputusan akuntansi.** Uji awal SO 68398 menunjukkan perubahan Status Channel di GET/UI tanpa perubahan SO/stock/asosiasi payment yang *teramati*, tetapi filter payment `q` tidak dapat menemukan payment yang diketahui ada. [Uji lanjutan SO 68399](accounting-one-shot-results.md) memiliki positive control jurnal baru dari invoice/payment; setelah satu edit, jumlah/ID jurnal terbaru dan detail dua jurnal terkait tetap sama, demikian pula SO/invoice/payment yang diperiksa. Cakupannya satu fixture, halaman jurnal terbaru dan jeda pembacaan singkat; posting tertunda dan edit vendor bersamaan tidak disangkal, serta stok sesudah edit tidak diukur. **Keputusan pemilik setelah meninjau batas ini:** akuntansi bukan lagi blocker peninjauan Ready; risiko residual diterima, **bukan** bukti keamanan finansial universal. Tetap fail-closed pada perbedaan uang/item/invoice/payment yang teramati; hentikan dan eskalasi bila efek samping muncul. Tidak ada izin implementasi, POST tambahan, atau rollout dari keputusan ini.
10. **Pemeliharaan.** Bila nanti disetujui, dokumentasikan alur, catatan investigasi, risiko provider, dan cron; ikuti kewajiban perubahan schema/seeder serta deployment bila jadwal/env berubah. Tidak ada endpoint publik baru atau UI marketplace dalam lingkup draf ini.

## Testing Decisions — seam dikonfirmasi pemilik

- **Seam utama:** operasi publik `reconcile mirror for order` (nama konseptual), diuji dengan PostgreSQL dan respons Jubelio terkontrol; nilai keluaran dan state persisten diperiksa lewat perilaku yang terlihat pada boundary layanan, tanpa mengekspos helper privat. Tes red → green per irisan vertikal. Pertahankan tes kontrak gateway HTTP pada boundary gateway yang sudah ada untuk create/edit dan GET. Tes tidak boleh menghubungi akun Jubelio atau mengirim POST nyata tanpa izin terpisah.
- **Create:** satu POST membawa `Belum Bayar`, satu GET independen memeriksa atribut inti sebelum Midtrans; create reject/ambigu/mismatch menahan checkout dan tidak membuat POST kedua. Jika hanya marker yang berbeda, uji checkout tetap boleh lanjut sambil menyimpan mismatch untuk investigasi, tanpa POST edit tambahan untuk marker awal.
- **Matriks status:** paid dengan verifikasi cepat → Siap Proses tanpa Menunggu Verifikasi; paid tetapi `in_flight`/`pending` → tidak ada marker manual review; paid + `manual_review`/blokir operator → Menunggu Verifikasi; `ready_for_pickup` tanpa invoice/payment terverifikasi → tidak ada Siap Proses; terminal failure, completed dan future cancelled hanya sesudah commit lokal; SO tidak ada → tidak ada edit; cancel SO aktif/terkonfirmasi → tidak ada POST edit Gagal Bayar dan mismatch tercatat persisten.
- **Race dan recovery:** dua pemanggil konkuren tidak mengirim lebih dari satu POST untuk intent yang sama; crash sesudah klaim, timeout, 5xx, body rusak, GET tidak cocok dan GET gagal → durable trace, tanpa POST ulang; sweep hanya GET untuk possibly-sent. Target terbaru tidak dikirim di belakang status lama yang belum selesai; late settlement setelah Gagal Bayar tidak membiarkan marker lama mengalahkan keadaan baru. Bukti kondisi ini harus menggunakan klaim PostgreSQL sungguhan, bukan hanya mock memori.
- **Payload/safety:** dengan SO ber-invoice/payment terverifikasi, payload edit menjaga nomor dan ID detail yang ada serta uang/item/source/lokasi; GET pasca-edit mengonfirmasi target dan atribut inti. Missing detail ID, remote mutation atau shape tidak lengkap menghasilkan **nol POST edit** dan kasus investigasi. Tidak ada tes yang menganggap mock provider atau satu respons 200 sebagai bukti tidak ada dampak akuntansi tersembunyi.
- **Noninterferensi:** gagal edit tidak mengubah status lokal, payment status, pickup code, atau izin verify-pickup; completion store tetap berhasil ketika cermin tidak tersedia. Uji penjadwalan ulang dan query operasional menemukan catatan persisten untuk order yang sudah selesai/terblokir, bukan hanya processing. Uji log terstruktur tidak berisi token/PII/raw body.
- **Prior art:** tes gateway satu POST + GET, tes operasi ledger PostgreSQL untuk klaim konkuren, tes settlement paid-but-blocked, serta tes recovery cron lewat HTTP sudah tersedia (lihat rujukan di bawah). Bila implementasi mengubah UI/routing, tambahkan Playwright sesuai kebijakan proyek; draf ini tidak mengubah UI. Untuk logika: jalankan tes terfokus lalu `npm run test:unit`; untuk perubahan routing/UI jalankan `npm run test:e2e` dengan prasyarat PostgreSQL. Tidak ada tes yang dijalankan untuk menyusun draf ini.

## Acceptance Criteria yang disetujui

1. Pada SO pickup `INTERNAL` baru yang terkonfirmasi, Status Channel dibaca sebagai Belum Bayar; SO create tetap hanya satu POST dan GET pengaman tetap memverifikasi hal-hal inti sebelum Midtrans.
2. Semua status pada tabel memetakan ke kejadian lokal yang telah commit; tidak ada Menunggu Verifikasi saat singkat in-flight dan tidak ada Siap Proses sebelum settlement terverifikasi + pickup siap.
3. Edit yang aman dikirim paling banyak sekali per intent/versi, dari full payload yang menjaga atribut wajib, lalu diverifikasi dengan GET; kegagalan atau hasil ambigu disimpan dan dapat dicari tanpa POST ulang otomatis.
4. Race dan crash tidak mengirim target basi setelah target baru; bukti ada dari tes PostgreSQL + respons provider terkontrol.
5. Sesudah create, setiap kegagalan cermin membiarkan pembayaran/pickup lokal berjalan menurut aturan lama; jalur cancel SO tidak ditunda atau dibalik demi Gagal Bayar, dan SO yang sedang/sudah dicancel tidak diedit untuk marker itu melainkan mismatch dicatat. Tidak menulis `is_paid`, `wms_status`, atau `fulfillment_blocked_reason` demi cermin.
6. Dokumentasi operasi menjelaskan cara menemukan mismatch, GET reconciliation, keterbatasan bukti finansial, serta tidak adanya izin retry/deployment implisit.

## Out of Scope

- Mengubah kolom **Status Jubelio**/WMS, `set-as-paid`, transisi WMS, pemalsuan sumber SHOPEE, atau memperlakukan channel marker sebagai bukti bayar/pickup.
- Implementasi jalur `cancelled` baru, pembatalan SO lama/test, penulisan ke SO uji 68394–68399, perubahan order delivery atau UI antrean admin.
- Migrasi/implementasi dalam permintaan penerbitan tiket ini, POST Jubelio (termasuk login), akses remote/SSH, commit, atau rollout tanpa izin terpisah. Tiket build lokal diterbitkan hanya di lokasi yang dipilih pemilik setelah approval breakdown; tiket tidak memberikan izin provider write/remote/commit.
