# Research: agent planning and Matt Pocock's development skills

Scope: historical investigation. The proposals below were researched before the local workflow was adopted; the current rules now live in [`AGENTS.md`](../../AGENTS.md), the [`development-workflow` skill](../../.agents/skills/development-workflow/SKILL.md), and [`plan/README.md`](../../plan/README.md). This research document grants no implementation authority. Sources were checked against Matt Pocock's own [skills repository](https://github.com/mattpocock/skills) (the `main` branch at research time); upstream skill files, rather than third-party workflow wrappers, are the authority. Upstream files can change; follow the links for the latest text.

## Former project workflow and the alignment gap (before the new gates)

- [`AGENTS.md` §4](../../AGENTS.md) requires **plan → execute → review** for behavior-affecting changes, but does not prescribe a user confirmation of the proposed scope, alternatives, or acceptance criteria before a plan is written. This is a process rule, not a requirement to make a `plan/` file for every small change.
- [`plan/README.md`](../../plan/README.md) reserves `plan/` for multi-feature conceptual plans and [`tasks.md`](../../tasks.md) for small work. It defines `Draft → Ready` as a complete plan **reviewed by the orchestrator**, not approved by the owner. `Ready` is eligible for implementation by an orchestrator/loop. The [`plan/_template.md`](../../plan/_template.md) has an `Open questions` section, but no mandatory resolution/owner approval before `Ready`. Therefore an agent can write a coherent but unwanted plan, self-review it, and mark it implementable. This is a process vulnerability inferred from the written rules, **not** proof that a particular agent took this path.
- Existing installed skills include [`.agents/skills/grill-me/SKILL.md`](../../.agents/skills/grill-me/SKILL.md) and [`.agents/skills/to-spec/SKILL.md`](../../.agents/skills/to-spec/SKILL.md). `grill-me` is explicitly user-invoked; `to-spec` explicitly **does not interview**: it synthesizes the conversation, checks testing seams with the user, then publishes to an issue tracker with `ready-for-agent`. There is no requirement there for the owner to sign off on the complete spec. Neither skill is automatically a gate on `plan/`'s status transitions. The repo also has TDD and systematic-debugging skills, but no installed local `grill-with-docs`, `to-tickets`, or `implement` skill in `.agents/skills/` at research time.
- [`AGENTS.md` §4](../../AGENTS.md) prohibits subagents, remote actions and pushes without explicit user direction. This differs from several of Matt's default skills (research/code-review use subagents; implement commits). Preserve these project restrictions in any adaptation.

## Matt's documented flow, step by step

The author's [README](https://github.com/mattpocock/skills/blob/main/README.md) describes a **composable, conditional** set of skills, not an automatic mandatory pipeline. User-invoked skills start distinct phases; model-invoked skills provide discipline inside them. Its main path is also stated in the [grill-with-docs](https://github.com/mattpocock/skills/blob/main/docs/engineering/grill-with-docs.md), [to-spec](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-spec.md), [to-tickets](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-tickets.md) and [implement](https://github.com/mattpocock/skills/blob/main/docs/engineering/implement.md) documentation:

| Stage | Skill(s) | What happens / human checkpoint |
|---|---|---|
| 0. One-time repository setup, if tracker-dependent flow is wanted | `/setup-matt-pocock-skills` | Configures tracker, labels and domain-doc layout; not part of each feature. [Source](https://github.com/mattpocock/skills/blob/main/docs/engineering/setup-matt-pocock-skills.md). |
| 1. Route the request (optional) | `/ask-matt` | Recommends a flow and stops; it does not execute its recommendation. Check actual skills before trusting its summary. [Source](https://github.com/mattpocock/skills/blob/main/docs/engineering/ask-matt.md). |
| 2. Align on what to build | `/grill-with-docs` → `grilling` + `domain-modeling` (in a repo); `/grill-me` → `grilling` (without repo) | Interview in dependency-aware rounds: ask only decisions whose prerequisites are resolved, recommend answers, leave decisions to the user; verify repo facts rather than asking the user. Terms go into `CONTEXT.md`; irreversible/surprising trade-offs may go into ADRs. **Stop before acting until shared understanding is confirmed.** [Grilling source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/grilling/SKILL.md), [grill-with-docs source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/grill-with-docs/SKILL.md), [domain-doc behavior](https://github.com/mattpocock/skills/blob/main/docs/engineering/grill-with-docs.md). |
| 2a. Settle uncertainty with an artifact (optional) | `prototype`; `research` | Prototype compares runnable behavior/UI alternatives; research verifies external facts against primary sources. These are aids to a decision, not permission to make the decision on the user's behalf. [Prototype source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/prototype/SKILL.md), [research described in README](https://github.com/mattpocock/skills/blob/main/README.md). |
| 3. Record settled requirements | `/to-spec` | Explore repo, propose testing seams and **check those seams with the user**, synthesize problem, solution, stories, prior decisions, tests and out-of-scope, publish to configured tracker. **It does not interview again** and its upstream source does not explicitly require approval of the *whole final spec* before publishing. If the conversation was misaligned, this step will not fix it. [Source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-spec/SKILL.md). |
| 4. Slice work if it spans sessions | `/to-tickets` | Draft independently verifiable vertical **tracer bullets**, each with blockers; **quiz the user on granularity, dependencies, merge/split, and iterate until approved before publishing**. Skip tickets when a change fits one context window. [Source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-tickets/SKILL.md). |
| 5. Build one decided slice | `/implement` → `tdd` | Read spec/ticket, test at pre-agreed seams, run typechecks and targeted tests repeatedly, full suite once, review and commit to current branch. Upstream `implement` **does not reopen planning**; it also commits by default, which must be adapted to local policy and dirty-worktree safety. [Source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/implement/SKILL.md), [operational caveats](https://github.com/mattpocock/skills/blob/main/docs/engineering/implement.md). |
| 6. Review against fixed baseline | `code-review` | Two separate axes: project standards and fidelity to the originating spec; upstream runs parallel subagents and compares committed diff against a fixed point. Those defaults need adaptation here because subagents require explicit permission, and an uncommitted diff may be missed. [Source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md), [review/commit mismatch](https://github.com/mattpocock/skills/blob/main/docs/engineering/implement.md). |

**Alternative on-ramps, not mandatory stages:** A large, foggy, multi-session effort may enter through `/wayfinder`: destination → decision map → one decision ticket/session → `/to-spec`; it plans rather than builds by default. A small change may skip spec/tickets after alignment and go directly to implementation. Incoming externally filed issues may use `/triage`, which recommends a state and **waits for the human** before applying it. Bugs use `diagnosing-bugs`: feedback loop → reproduce/minimize → hypotheses → instrumentation → fix/regression test → cleanup. [Wayfinder](https://github.com/mattpocock/skills/blob/main/docs/engineering/wayfinder.md), [to-tickets skip guidance](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-tickets.md), [triage](https://github.com/mattpocock/skills/blob/main/docs/engineering/triage.md), [diagnosing-bugs](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/diagnosing-bugs/SKILL.md).

## Proposal that informed the adopted local workflow

1. Add an explicit **alignment gate before any actionable plan/spec**: inspect code/facts, ask the owner about genuine choices and exclusions, summarize scope + observable acceptance criteria + non-scope, then await explicit confirmation. A draft must not be labelled `Ready` while decisions are unresolved.
2. Change `plan/README.md` so `Draft → Ready` means **owner-approved scope and acceptance criteria**, not merely self-review by the orchestrator; require an explicit confirmation before a loop can select a `Ready` plan. Keep existing `plan/index.md` status bookkeeping and docs/testing rules.
3. Add a short **read-back gate after the complete spec/plan**: show a concise decision summary, edge cases, exclusions and test evidence before publication/implementation; record what was approved. This is an intentional **project-specific improvement**, not a claim that upstream `/to-spec` already does it.
4. Only use tickets when work truly spans sessions; make ticket approval separate from plan approval, as upstream `/to-tickets` does. For a small bug, use reproduction/diagnosis then confirm the intended behavior and proceed to TDD rather than generating a multi-feature plan.
5. Preserve explicit prohibitions on unrequested subagents, remote actions and pushes. Choose whether commits themselves require approval; do not automatically import upstream `/implement`'s commit behavior, especially with an already-dirty worktree.

Example: if the request is “display branch stock on product pages”, first check the current stock schema and ask whether unavailable stock should be hidden or shown as zero (a product decision); read back “per-branch quantity shown; zero shown but cannot add to cart; no changes to checkout allocation”; get confirmation, **then** write the actionable spec/plan and only move it to `Ready` after the owner approves its acceptance criteria. A technically elegant aggregate-stock plan should not silently become `Ready` when pickup is branch-specific.

## Limitations

This is documentation research, not observation of Matt's private sessions or a promise that every upstream skill always behaves as intended. The upstream docs themselves report gaps: decisions kept only in a grilling conversation can be lost when context is cleared; `to-spec` does not explicitly confirm the full final spec; `implement` can run code-review before the code is committed even though code-review compares commits; and ticket closure is not automatic. See the linked upstream pages above. No application tests were run because no behavior-affecting code was changed.
