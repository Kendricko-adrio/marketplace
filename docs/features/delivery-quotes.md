# Delivery checkout quotes

Checkout follows **Cara Pengiriman → Bayar & Pesan** (dua langkah; langkah **Kontak** dilebur ke langkah pertama, lihat [Kontak pesanan dan navigasi](#kontak-pesanan-dan-navigasi)). Step 1 offers pickup or delivery from one branch and shows the selected items with an **Ubah** link back to the cart. Pickup remains the initial method. The customer must validate the pickup date/time or explicitly select a ready delivery service before the review; the existing pickup endpoint retains its `/api/checkout/validate-step-2` name for compatibility. Both method cards place their title above a separate description with a 4px gap and relaxed line height, keeping wrapped text readable on desktop and mobile. Delivery uses either an owned saved address or a new address entered in a modal (optionally saved at approved order placement); the backend revalidates its Shipment region chain. An existing default address is selected automatically unless the customer changes destination. Server-derived current cart prices, quantities, SKU parcels and local branch origin remain authoritative. No browser-provided weight, price, courier fee or recipient region is trusted. Halaman checkout tidak lagi menampilkan panel ringkasan di samping: seluruh perhitungan (subtotal, PPN, ongkir, subsidi, promo, total) hanya ada di **Rincian Pembayaran** pada langkah **Bayar & Pesan**, sehingga langkah input menjadi satu kolom penuh.

## Pemilihan alamat di checkout

Bagian **Alamat Pengiriman** menggunakan shared Button `outline` dengan ikon **+** dan label **Gunakan alamat baru**, bukan action yang menyerupai teks biasa. Tombol memenuhi lebar kolom pada mobile, memiliki indikator keyboard focus, serta menandai state dialog melalui `aria-haspopup="dialog"`, `aria-expanded`, dan `aria-controls`. Bila buku alamat kosong, dropdown disembunyikan dan pesan **Belum ada alamat tersimpan. Tambahkan alamat pengiriman lewat tombol di bawah.** mengarahkan pelanggan untuk mengisi alamat tanpa meninggalkan checkout. Loading dan kegagalan memuat alamat dibedakan dari buku alamat kosong; kegagalan tetap menyediakan **Coba lagi**.

Form alamat baru hidup di dalam **modal** (shared `Dialog`), bukan form inline yang memanjangkan halaman. Modal memakai judul **Alamat baru**, satu `DialogTitle` saja (tanpa judul ganda), fokus awal pada field **Nama Penerima**, serta isi yang bisa di-scroll dengan footer melekat sehingga **Batal**/**Gunakan alamat ini** selalu terjangkau pada 390 px. Selama modal terbuka, halaman di belakang tidak dapat diklik (modal focus trap), dan tombol **Gunakan alamat ini** nonaktif sampai nama, telepon, wilayah, dan alamat lengkap; teks bantuan di footer menjelaskan alasannya.

Semantik draft vs terpakai dijaga: mengetik di modal **tidak** memicu quote, `Batal`/tombol tutup membuang draft itu, dan hanya **Gunakan alamat ini** yang menetapkan alamat tujuan lalu memicu quote otomatis. Membuka ulang modal menampilkan alamat yang sedang terpakai, sehingga edit yang dibatalkan tidak diam-diam dipakai. Setelah diterapkan, kartu **Alamat baru terpakai** menampilkan penerima, telepon, alamat, kode pos, status simpan, dan tombol **Ubah alamat**; memilih alamat tersimpan dari dropdown mengembalikan tujuan ke alamat tersebut dan menutup status alamat baru. Checkbox **Simpan alamat** dan **Jadikan alamat utama** tetap berada di dalam modal dan hanya berpengaruh saat order diterima. Nomor penerima menggunakan input telepon. Petunjuk di dekat **Periksa ongkir** menjelaskan perlunya memilih alamat atau layanan sebelum **Lanjut** tersedia. Saat request berlangsung, label tombol menjadi **Memeriksa ongkir…**.

Coverage UI: `e2e/store/delivery-quote-mock.spec.ts` memeriksa buku alamat kosong pada desktop/mobile (1280/390 px), aktivasi tombol melalui Enter dengan fokus masuk ke field pertama, draft yang tidak memicu quote sebelum diterapkan, `Batal` yang tidak mengubah tujuan terpakai, edit yang menurunkan pilihan layanan setelah diterapkan, ketiadaan overflow horizontal, serta `e2e/store/delivery-order-mock.spec.ts` untuk alamat baru tanpa simpan maupun simpan-sebagai-default. Referensi komponen: shared `Dialog` (pola dialog penggantian promo di checkout) dan form `/account/addresses`.

Context7 checkpoint: `/microsoft/playwright` — `toHaveCSS`, `toBeFocused`, serta aktivasi tombol melalui keyboard diverifikasi terhadap dokumentasi Playwright. Perubahan UI memakai komponen internal dan atribut HTML standar; tidak menambah API framework atau backend.

## Kontak pesanan dan navigasi

Langkah pertama mengumpulkan kontak pesanan sekaligus, sehingga tidak ada lagi langkah **Kontak** terpisah. **Pickup** menampilkan field **Nomor Telepon \*** dan **Email \*** (terisi dari sesi, dapat diubah, dengan aksi **Isi dari Profil** serta validasi 8–15 angka dan format email). **Delivery** tidak menampilkan input kontak: email pesanan memakai email akun secara **read-only**, sedangkan telepon pemesan mengikuti nomor penerima pada alamat terpilih (read-only). Tombol **Lanjut** memvalidasi kontak lebih dulu; bila nomor penerima pada alamat tidak lolos aturan 8–15 angka, pesan error menyuruh memperbaiki nomor di Buku Alamat atau memakai alamat baru, dan order tidak pernah dibuat dengan kontak tidak valid.

Pesan gugur kontak bersifat method-neutral dan tetap dekat dengan field-nya. Pickup menampilkan satu pengingat pengambilan serta menjelaskan bahwa kode pickup dikirim ke email setelah pesanan siap. Delivery tidak menampilkan instruksi pickup. Langkah **Bayar & Pesan** memberi label **Kontak Pemesan** dan **Penerima Pengiriman** untuk nilai yang sama seperti sebelumnya.

Back/forward navigation preserves pickup slots, kontak pickup, saved/new destination, save/default intent dan layanan delivery terpilih selama input quote tidak berubah. Panel fulfillment tetap ter-mount (hidden) di luar langkah 1, jadi berpindah langkah tidak memicu requote atau menghapus draft lokal. Perubahan metode/tujuan/cart tetap menggugurkan pilihan layanan dan uang. Respons validasi pickup yang terlambat tidak boleh melompatkan customer ke langkah pembayaran setelah metode atau slot berubah; hanya validasi terbaru untuk input yang tidak berubah yang diterima. Meninggalkan langkah pembayaran me-reset konfirmasi; kembali ke sana menuntut persetujuan baru. Reprice saat place-order memperbarui panel dan review tanpa submit otomatis; layanan yang hilang mengembalikan customer ke **Cara Pengiriman**.

**Satu slot promo di langkah terakhir.** Pilihan kupon publik maupun **Manual Promo Code** hanya muncul di langkah **Bayar & Pesan** untuk pickup dan delivery; state gugur (`Promo sebelumnya tidak lagi berlaku` + **Lanjut tanpa promo**), dialog kenaikan total, dan acknowledgement place-order tidak berubah. Karena permukaan promo hanya satu, banner gugur yang dulu diduplikasi di kartu pesanan dihapus. Bila review server gugur (promo ditolak, `CHECKOUT_REVIEW_REQUIRED`, atau `DELIVERY_REPRICE_REQUIRED` yang layanannya masih ada), customer tetap di langkah pembayaran dan melihat banner **Rincian pesanan perlu diperiksa ulang** dengan tombol **Periksa ulang pesanan** yang membuat review baru di tempat; tombol **Bayar Sekarang** nonaktif sampai review baru ada.

API contracts, pricing, address persistence dan payment integration tidak berubah.

## Quote contract

`POST /api/checkout/delivery-quote` requires an onboarded store session and strict body `{ itemIds: string[], addressId: string }` **or** `{ itemIds: string[], newAddress: ClientAddressInput }`. Quoting a new address never writes it to the book; `saveAddress` is only considered during final approved order placement. Successful response is `{ success: true, data: { services } }`; each service has courier/service IDs, `serviceCategoryId: number | null`, name, `shippingCost`, pricing strings, an opaque `originFingerprint`, and optional valid ETA. Category metadata is normalized from vendor `courier_service_category` (positive safe-integer ID, numeric ID string, or an exact official category name); absent/malformed metadata becomes null. Unknown positive IDs are preserved but displayed in Lainnya. Missing metadata never excludes an otherwise usable service. Missing/foreign resources return 404, invalid/unready data 400, failed/no-service quote 502. No quote ID, TTL, background refresh or zero/stale fee fallback is invented.

The separate server-side Shipment adapter uses `JUBELIO_SHIPMENT_URL`, `JUBELIO_SHIPMENT_CLIENT_ID`, and `JUBELIO_SHIPMENT_CLIENT_SECRET`. It obtains a token through `/auth/generate-token`, respects token expiry, and posts measured per-item quantities/grams/cm to `/rates/all`. Rates requests send zip/area and measurement fields only, not recipient contacts or an invented carton. There is no retry/live fallback. E2E mode requires a bare HTTP loopback origin and is prohibited by either APP_ENV or NODE_ENV production. Logs never contain tokens, addresses or raw provider responses.

The customer pays exactly vendor **rates**, never **final_rates**. Delivery PPN is calculated on goods plus shipping using the existing website rate/rounding. For goods Rp100,000, rates Rp20,000 and PPN 11%, PPN is Rp13,200 and total Rp133,200 even if final_rates is Rp10,000. Nonempty opaque insurance_info is excluded until vendor semantics are known; shipping_insurance amounts alone are not interpreted as mandatory insurance. ETA is optional. No insurance premium is added.

The checkout courier picker is a compact inline native radio group with six horizontally scrollable category filters: **Semua · Termurah** (default), **Reguler/Ekonomi** (Jubelio IDs 1/2), **Next Day** (3), **Same Day** (5), **Instant** (4), and **Lainnya** (Cargo 6, full truck 7, unknown IDs or missing metadata). Categories come exclusively from provider metadata, never the carrier name or ETA. Each filter shows the count across the full current quote; zero-count filters are disabled with "Tidak tersedia untuk alamat ini". Category switching is client-side and makes no new provider request.

Services are filtered before sorting by `shippingCost` ascending and client-side pagination (five options per page on desktop and mobile; equal-price options keep provider order). Every row shows the service name, Rupiah ongkir and arrival estimate; all minimum-price options **within the active filter** receive a "Termurah" badge. No service is auto-selected. Pagination shows the visible range and filtered total, with previous/next controls only when multiple pages exist. Switching category resets the page to one but preserves the selected service and checkout summary, as does page navigation. An off-page or off-category choice is identified as "Terpilih: <service>". Selection identity uses both courier and service IDs.

ETA is displayed as an Indonesian arrival date/range in `Asia/Jakarta` (WIB), without raw timestamps or an invented day-count duration: for example, `2026-10-06T09:18:03.751Z` through `2026-10-11T09:18:03.751Z` becomes "Estimasi tiba 6–11 Okt 2026". A same-day estimate shows one date; cross-month/year ranges retain the necessary month/year context. Next Day/Same Day are provider service categories, not promises of arrival tomorrow/today; the provider's actual arrival estimate remains visible even if it is several days away. Missing, invalid or reversed estimates show "Estimasi tiba belum tersedia".

Address/cart fingerprint changes discard service selection and displayed quote money, reset the category to Semua and pagination to page one, disable continuation and request fresh options. Explicit requotes and order-reprice pushes also restore the default category/page. Late responses are discarded. The customer must select a service again after an address/cart change. Failure offers retry or pickup. Only the checkout Ringkasan displays the selected server PPN and total (there is no duplicate money summary under the picker), never stale cart prices; without a selected delivery service, totals are withheld. Display filtering/sorting/pagination does not change backend rates, pricing, order approval, revalidation or the persisted order snapshot. Quote-success logs include distinct category and uncategorized-service counts, never raw provider metadata. The local Shipment mock's regular fixture includes category ID 1.

New quotes and checkout approval require a complete stored Shipment origin hierarchy, canonical names/postcode and digit-string Area ID, as well as existing active/sender/parcel prerequisites. Incomplete origins are rejected before rates calls with a request to complete branch shipping configuration. Every new rates request carries the selected origin `area_id`; no hierarchy lookup is added per origin quote. Services bind approval to the origin IDs/names/postcode through `originFingerprint`, which must be returned unchanged at order placement. Changing the origin forces 409 fresh approval even when rates and postcode are unchanged. Legacy pickup and accepted order snapshots remain unaffected. See [branch regions](branch-shipping-regions.md).

Delivery order placement revalidates the quote and freezes immutable snapshots; see [delivery orders](delivery-orders.md). Booking reconciliation is a subsequent slice. Pickup remains functional.
