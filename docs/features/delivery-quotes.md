# Delivery checkout quotes

Checkout follows **Cara Pengiriman → Informasi Kontak → Bayar & Pesan**. Step 1 offers pickup or delivery from one branch and shows the selected items with an **Ubah** link back to the cart. Pickup remains the initial method. The customer must validate the pickup date/time or explicitly select a ready delivery service before proceeding to contact; the existing pickup endpoint retains its `/api/checkout/validate-step-2` name for compatibility. Both method cards place their title above a separate description with a 4px gap and relaxed line height, keeping wrapped text readable on desktop and mobile. Delivery uses either an owned saved address or a new address entered inline (optionally saved at approved order placement); the backend revalidates its Shipment region chain. An existing default address is selected automatically unless the customer changes destination. Server-derived current cart prices, quantities, SKU parcels and local branch origin remain authoritative. No browser-provided weight, price, courier fee or recipient region is trusted.

## Order contact and navigation

Step 2 requires an active order-contact phone and email for both methods, retaining session autofill and **Isi dari Profil**. Contact validation errors are method-neutral. Pickup shows one collection reminder and explains that the pickup code is emailed only once the order is ready. Delivery shows no pickup instructions: the order contact belongs to the purchaser, while shipment uses the separate recipient name/phone on the chosen destination. Neither contact overwrites the other. Review labels these as **Kontak Pemesan** and **Penerima Pengiriman**.

Back/forward navigation preserves contact inputs, pickup slots, saved/new destination, inline save/default intent and the selected delivery service when the quote inputs are unchanged. The fulfillment panel stays mounted but hidden outside step 1, so merely changing steps does not requote or lose the local draft. Method/destination/cart changes still invalidate delivery selection and money. Late pickup-validation responses cannot advance after the method or pickup slot changes; only the latest validation of unchanged inputs is accepted. Leaving review clears confirmation; returning requires a fresh approval. Order-time reprice updates the retained panel and review without automatic resubmission; a vanished service returns to **Cara Pengiriman** (step 1), not contact. API contracts, pricing, address persistence and payment integration are unchanged.

## Quote contract

`POST /api/checkout/delivery-quote` requires an onboarded store session and strict body `{ itemIds: string[], addressId: string }` **or** `{ itemIds: string[], newAddress: ClientAddressInput }`. Quoting a new address never writes it to the book; `saveAddress` is only considered during final approved order placement. Successful response is `{ success: true, data: { services } }`; each service has courier/service IDs, `serviceCategoryId: number | null`, name, `shippingCost`, pricing strings, an opaque `originFingerprint`, and optional valid ETA. Category metadata is normalized from vendor `courier_service_category` (positive safe-integer ID, numeric ID string, or an exact official category name); absent/malformed metadata becomes null. Unknown positive IDs are preserved but displayed in Lainnya. Missing metadata never excludes an otherwise usable service. Missing/foreign resources return 404, invalid/unready data 400, failed/no-service quote 502. No quote ID, TTL, background refresh or zero/stale fee fallback is invented.

The separate server-side Shipment adapter uses `JUBELIO_SHIPMENT_URL`, `JUBELIO_SHIPMENT_CLIENT_ID`, and `JUBELIO_SHIPMENT_CLIENT_SECRET`. It obtains a token through `/auth/generate-token`, respects token expiry, and posts measured per-item quantities/grams/cm to `/rates/all`. Rates requests send zip/area and measurement fields only, not recipient contacts or an invented carton. There is no retry/live fallback. E2E mode requires a bare HTTP loopback origin and is prohibited by either APP_ENV or NODE_ENV production. Logs never contain tokens, addresses or raw provider responses.

The customer pays exactly vendor **rates**, never **final_rates**. Delivery PPN is calculated on goods plus shipping using the existing website rate/rounding. For goods Rp100,000, rates Rp20,000 and PPN 11%, PPN is Rp13,200 and total Rp133,200 even if final_rates is Rp10,000. Nonempty opaque insurance_info is excluded until vendor semantics are known; shipping_insurance amounts alone are not interpreted as mandatory insurance. ETA is optional. No insurance premium is added.

The checkout courier picker is a compact inline native radio group with six horizontally scrollable category filters: **Semua · Termurah** (default), **Reguler/Ekonomi** (Jubelio IDs 1/2), **Next Day** (3), **Same Day** (5), **Instant** (4), and **Lainnya** (Cargo 6, full truck 7, unknown IDs or missing metadata). Categories come exclusively from provider metadata, never the carrier name or ETA. Each filter shows the count across the full current quote; zero-count filters are disabled with "Tidak tersedia untuk alamat ini". Category switching is client-side and makes no new provider request.

Services are filtered before sorting by `shippingCost` ascending and client-side pagination (five options per page on desktop and mobile; equal-price options keep provider order). Every row shows the service name, Rupiah ongkir and arrival estimate; all minimum-price options **within the active filter** receive a "Termurah" badge. No service is auto-selected. Pagination shows the visible range and filtered total, with previous/next controls only when multiple pages exist. Switching category resets the page to one but preserves the selected service and checkout summary, as does page navigation. An off-page or off-category choice is identified as "Terpilih: <service>". Selection identity uses both courier and service IDs.

ETA is displayed as an Indonesian arrival date/range in `Asia/Jakarta` (WIB), without raw timestamps or an invented day-count duration: for example, `2026-10-06T09:18:03.751Z` through `2026-10-11T09:18:03.751Z` becomes "Estimasi tiba 6–11 Okt 2026". A same-day estimate shows one date; cross-month/year ranges retain the necessary month/year context. Next Day/Same Day are provider service categories, not promises of arrival tomorrow/today; the provider's actual arrival estimate remains visible even if it is several days away. Missing, invalid or reversed estimates show "Estimasi tiba belum tersedia".

Address/cart fingerprint changes discard service selection and displayed quote money, reset the category to Semua and pagination to page one, disable continuation and request fresh options. Explicit requotes and order-reprice pushes also restore the default category/page. Late responses are discarded. The customer must select a service again after an address/cart change. Failure offers retry or pickup. Only the checkout Ringkasan displays the selected server PPN and total (there is no duplicate money summary under the picker), never stale cart prices; without a selected delivery service, totals are withheld. Display filtering/sorting/pagination does not change backend rates, pricing, order approval, revalidation or the persisted order snapshot. Quote-success logs include distinct category and uncategorized-service counts, never raw provider metadata. The local Shipment mock's regular fixture includes category ID 1.

New quotes and checkout approval require a complete stored Shipment origin hierarchy, canonical names/postcode and digit-string Area ID, as well as existing active/sender/parcel prerequisites. Incomplete origins are rejected before rates calls with a request to complete branch shipping configuration. Every new rates request carries the selected origin `area_id`; no hierarchy lookup is added per origin quote. Services bind approval to the origin IDs/names/postcode through `originFingerprint`, which must be returned unchanged at order placement. Changing the origin forces 409 fresh approval even when rates and postcode are unchanged. Legacy pickup and accepted order snapshots remain unaffected. See [branch regions](branch-shipping-regions.md).

Delivery order placement revalidates the quote and freezes immutable snapshots; see [delivery orders](delivery-orders.md). Booking reconciliation is a subsequent slice. Pickup remains functional.
