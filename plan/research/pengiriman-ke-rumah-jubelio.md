# Riset: pengiriman ke rumah dari checkout pickup-in-store

**Status:** riset dan rekomendasi; **belum ada perubahan aplikasi, skema, integrasi, atau deployment**. Fokus: storefront memilih pengiriman ke alamat rumah, operasional mengirim melalui kurir, tanpa merusak alur ambil di cabang. Sumber utama: transkripsi kontrak Jubelio Shipment v1.8 [`docs/jubelio-api/shipment-v1.8.md`](../../docs/jubelio-api/shipment-v1.8.md) (merujuk halaman PDF kontrak v1.8 yang disebut di transkripsi; **berkas PDF sumber tidak ada di working tree saat pemeriksaan ini**), spesifikasi **Omnichannel yang terpisah** [`docs/jubelio-api/dist.yaml`](../../docs/jubelio-api/dist.yaml) (rujukan baris di bawah), dan implementasi repo. Kontrak v1.8 mencantumkan pembuatan token, tarif, AWB, tracking, serta webhook; **bukan bukti bahwa fitur Shipment aktif untuk tenant ini, kontrak tersebut masih mutakhir, atau integrasi pesanan website telah teruji**. Tidak ada panggilan API ke akun Jubelio, pembuatan resi, atau uji transaksi dalam riset ini.

## 1. Kesimpulan utama dan batas kepastian

1. **Bisa dirancang sebagai dua metode fulfillment**, `pickup` (tetap ada) dan `delivery`; pertahankan kepemilikan stok pada **satu cabang asal** per order sampai ada desain split shipment. Sekarang checkout menolak cart lintas cabang, memilih slot pickup, mengisi `shippingCost: 0`, dan pembayaran yang berhasil langsung memberi status `ready_for_pickup` serta kode pickup. [Repo: `place-order/route.ts` L53–56, L144–171, L212–213, L265–268; `order-finalize.ts` dijelaskan dalam `docs/features/order-flow.md` §Happy path](../../docs/features/order-flow.md).
2. **Kontrak Jubelio Shipment v1.8 kini tersedia di repo**: API tersendiri di `api-shipment.*.jubelio.com` menyediakan `POST /rates` (satu kategori layanan), `POST /rates/all` (lintas kurir), `POST /shipments/create` (AWB), `GET /shipments/awb/{awb}` (detail + timeline), serta webhook status (lihat §3a). Ini mengubah temuan lama: **ketiadaan quote/booking/tracking di `dist.yaml` hanya berlaku untuk spesifikasi Omnichannel**, bukan untuk Shipment. Kontrak **tidak mencantumkan endpoint pembuatan label** dan berbeda dari beberapa path yang digunakan plugin WooCommerce. Jangan menjanjikan tarif live, layanan/ETA tertentu, atau tracking realtime sampai akses tenant, semantik tarif, dan happy path sandbox tervalidasi. [Shipment v1.8: PDF pp. 1–21; Omnichannel: `dist.yaml` bagian `paths`](../../docs/jubelio-api/shipment-v1.8.md).
3. **AWB Omnichannel tidak sama dengan booking Shipment.** `POST /sales/request-awb-order/` hanya menerima `salesorder_id`, respons mencontohkan `shipper: JNE Cashless`, `tracking_no`, `channel_order_detail_id`, `package_id`; dari contoh channel ini **tidak dapat disimpulkan bahwa ia akan menghasilkan resi untuk Sales Order internal website**. `POST /wms/sales/shipments/orders/` menyajikan data AWB berdasar IDs, dan `POST /sales/orders/save-airwaybill/` justru menyimpan resi yang sudah ada. Tiga operasi itu tidak boleh dianggap sebagai API quote/book tanpa konfirmasi eksplisit. [Spec L2865–2891, L9472–9505, L12802–12860, L9052–9077, L26325–26343, L27364–27390].
4. **Keputusan UX rilis awal:** pengiriman memakai **form alamat lengkap berbasis wilayah Jubelio + buku alamat dengan alamat utama (`isDefault`)**, tanpa pin peta/OpenStreetMap. Koordinat opsional pada API Shipment bukan pengganti alamat/kode pos; pertimbangkan peta nanti hanya jika kebutuhan last-mile terbukti (lihat §3b). Pertahankan pilihan pickup atau kirim; rilis otomatis **hanya setelah** aktivasi Shipment, aturan tarif/idempotensi, dan alur sandbox untuk order website tervalidasi. Label tetap perlu jalur terpisah yang dikonfirmasi. Pilot **tarif tetap + booking manual** hanya bila operasi/pembayaran/rekonsiliasi dan risiko selisih biaya disetujui.

### 3a. Kontrak API Jubelio Shipment v1.8 (sumber utama)

Sumber: [`shipment-v1.8.md`](../../docs/jubelio-api/shipment-v1.8.md), transkripsi PDF kontrak v1.8 (berkas PDF sumber **tidak ada di working tree saat pemeriksaan ini**), **bukan hasil panggilan live**. Base URL produksi `https://api-shipment.jubelio.com`, sandbox `https://api-shipment.sandbox.jubelio.com`; bukan host `api2.jubelio.com` milik Omnichannel. Minta `client_id`/`client_secret` Shipment tersendiri; `POST /auth/generate-token` menghasilkan `token` dan contoh `expires_in: 86400` detik (tabel tipe menyebut string, contoh angka). Bearer token digunakan pada operasi terautentikasi; kontrak tidak eksplisit memperlihatkan header auth pada semua GET wilayah/kategori. Simpan kredensial dan token di server, refresh sebelum kedaluwarsa. [PDF pp. 1–2, 9–18](../../docs/jubelio-api/shipment-v1.8.md)

Jangan menurunkan charge pelanggan dari `final_rates` atau menganggap `price` booking sama persis dengan `rates` tanpa uji. Tidak ada jaminan quote TTL, idempotency booking, tarif final, daftar kode kurir, rate limit, maupun kebijakan retry dalam PDF. [PDF pp. 2–4, 14–19](../../docs/jubelio-api/shipment-v1.8.md)

**Koordinat bukan kebutuhan rilis awal:** `origin.coordinate` dan `destination.coordinate` bersifat opsional pada quote dan create AWB; contoh kontrak memakai string `(latitude,longitude)` tetapi format persis dan penggunaannya oleh kurir perlu uji sandbox. Untuk keputusan rilis awal, **jangan kirim `coordinate`**; gunakan alamat lengkap, kode pos dan `area_id` Shipment yang terverifikasi. [PDF pp. 2–4, 14–18](../../docs/jubelio-api/shipment-v1.8.md)

**Label dan path plugin:** v1.8 **tidak mendokumentasikan endpoint label**. [Kode klien plugin WooCommerce](https://plugins.svn.wordpress.org/jubelio-shipment/trunk/includes/classes/class-jubelioshipment-api.php) sebelumnya memakai `POST /webstore/rates/all`, `GET /shipments/{shipment_id}`, dan `POST /shipments/generate-shipping-label`; **jangan menggantikan** path kontrak `/rates/all` dan `/shipments/awb/{awb}` dengan path plugin atau menganggap endpoint label plugin dijamin kontrak v1.8. `GET /reports/shipping-label/` di Omnichannel juga bukan bukti label bagi AWB Shipment. Minta kontrak/izin label terkini secara terpisah. Plugin mengatur `webstore_id` opsional, namun kontrak v1.8 tidak menjelaskan kaitan Shipment dengan Sales Order Omnichannel dan efek stoknya; jangan mengasumsikan SO wajib ataupun stok otomatis sinkron. Staging marketplace [dapat menulis stok Jubelio live](../../docs/deployment-docs/jubelio-sync.md), jadi uji hanya pada sandbox/kredensial dan data yang dipastikan terisolasi.

### 3b. Keputusan UX alamat: rilis awal tanpa pin peta

**Diputuskan dalam diskusi produk:** gunakan **form penuh** dan alamat tersimpan sebagai default; **OpenStreetMap/pin peta ditunda**, bukan syarat checkout. Ini keputusan scope produk, bukan batasan teknis API: Shipment menerima koordinat opsional, tetapi untuk tarif mewajibkan `origin.zipcode`/`destination.zipcode`, sedangkan pembuatan AWB mewajibkan `name`, `phone`, `address`, dan `zipcode` untuk pengirim/penerima. `area_id` opsional pada request, tetapi direkomendasikan dari lookup wilayah Shipment untuk akurasi pemetaan. [PDF pp. 2–4, 9–18](../../docs/jubelio-api/shipment-v1.8.md)

**Alur form rilis awal:**

1. Pelanggan memilih provinsi → kota/kabupaten → kecamatan → kelurahan/area **dari API Shipment** (atau pencarian `/regions?name=…` yang hasilnya diverifikasi). Simpan pasangan ID/nama wilayah dan `area_id` sebagai **string**, serta kode pos yang dikembalikan, dengan kesempatan pelanggan memeriksa detailnya. Jangan menyamakan ID dari API Omnichannel atau geocoder peta dengan ID Shipment. Backend memvalidasi ulang hubungan area–kode pos dan kepemilikan alamat tersimpan sebelum quote/booking; jangan percaya ID atau kode pos kiriman browser semata. [PDF pp. 9–14](../../docs/jubelio-api/shipment-v1.8.md)
2. Pelanggan mengisi **nama penerima, telepon, jalan/nomor rumah, detail gedung/unit dan patokan bila perlu, kode pos**, lalu boleh mencentang **Simpan alamat** dan **Jadikan alamat utama**. Detail tertulis tetap diperlukan meski suatu hari ada pin. Asal cabang juga memerlukan nama/kontak/alamat/kode pos valid untuk create AWB. [PDF pp. 2–4](../../docs/jubelio-api/shipment-v1.8.md)
3. Checkout berikutnya memilih alamat utama otomatis; pelanggan boleh mengganti alamat atau membuat yang baru. Pastikan **maksimal satu alamat utama per client**, operasi set-default atomik dan scoped ke pemilik, serta pilihan alamat ditinjau ulang sebelum bayar. Tabel `address` sudah memiliki `isDefault`, tetapi **belum ada UI/API buku alamat**; implementasi dan constraint/perilaku default tetap harus dirancang. Simpan **snapshot alamat pada order** agar edit/hapus alamat tersimpan tidak mengubah tujuan order lama. [Repo: `orders.ts` L18–46](../../packages/db/src/schema/orders.ts).

**Opsi fase berikutnya (belum diputuskan untuk dikerjakan):** pin bisa membantu lokasi last-mile seperti pintu apartemen/gang, bukan menentukan ongkir atau menggantikan form. Jika kelak dipakai, pin dan `area_id` tidak boleh digabung tanpa pemeriksaan server: contoh area Bandung + pin Rusia harus ditolak; selisih dekat batas wilayah perlu konfirmasi. Kontrak Shipment **tidak menyediakan polygon area** untuk mencocokkan pin dengan `area_id`; reverse geocoding hanya mencari objek terdekat dan dapat memberi alamat yang keliru ([Nominatim Reverse](https://nominatim.org/release-docs/latest/api/Reverse/)). Jangan menganggap kode pos atau hasil reverse-geocode saja sebagai bukti geometris. Layanan Nominatim **publik** melarang autocomplete, membatasi total trafik aplikasi maksimal 1 request/detik, meminta identitas/atribusi dan melarang pengiriman data pribadi; tile OSM publik best-effort dengan aturan atribusi/caching, **bukan layanan SLA produksi** ([kebijakan Nominatim](https://operations.osmfoundation.org/policies/nominatim/), [kebijakan tile OSM](https://operations.osmfoundation.org/policies/tiles/)). Bila nanti peta dibutuhkan, validasi batas wilayah dan pilih penyedia/hosting yang sesuai sebelum mengirim koordinat ke Shipment; jangan membuat pelanggan bergantung pada peta untuk checkout.

## 7. Rancangan alur dan titik integrasi

1. **Sebelum checkout:** tentukan origin dari cart satu cabang dan profil paket. Pilih pickup atau delivery. Pada delivery, pilih alamat utama tersimpan atau isi form penuh lalu simpan jika diinginkan; backend validasi pemilik alamat serta petakan ulang wilayah/area dan kode pos melalui **Shipment** (`/regions` atau hierarki `/region/*`, bukan ID Omnichannel tanpa verifikasi). **Tidak memerlukan atau mengirim pin/koordinat pada rilis awal.** Ambil `/rates/all` atau `/rates` dari server dan ikat snapshot pilihan `courier_id` + `courier_service_id`, `rates`, asal, tujuan, berat, cart hash, serta waktu perhitungan ke user. **Tidak ada quote ID/TTL dalam v1.8**: masa berlaku dan re-quote adalah kebijakan aplikasi yang harus diuji dengan vendor.
2. **Place order:** server baca ulang cart/stok/akses alamat, minta ulang quote bila perlu dan validasi ketersediaan layanan/harga `rates` (bukan `final_rates`), tetapkan kebijakan bila tarif berubah, buat snapshot alamat+pilihan layanan dan shipping charge; simpan order pending payment dan hold stok sesuai saga sekarang. Jangan order kurir saat `pending_payment`: order bisa expired/ditolak dan menimbulkan resi/tagihan tak sah. Buat Snap dengan ongkir di item details, dan ulangi snapshot yang sama saat re-payment. [Repo: `order-flow.md` §Happy path, §Re-payment](../../docs/features/order-flow.md).
3. **Settlement Midtrans:** klaim pembayaran idempotent seperti sekarang; **pickup** tetap menuju `ready_for_pickup`, **delivery** menuju `paid_awaiting_fulfillment`/`packing` (nama akhir diputuskan), tanpa pickup code/email siap ambil. Enqueue tindakan kirim durable setelah commit; bila Jubelio down, uang/order tetap terlihat dan masuk exception queue, bukan hilang.
4. **Fulfillment:** staf cabang konfirmasi barang; kirim `POST /shipments/create` dari backend dengan `ref_no`, pasangan ID kurir/layanan yang dipilih, data pengirim-penerima serta `items[]`. Simpan `shipment_id`, `awb`, `tracking_url`, dan `price`; rekonsiliasi dengan `rates` yang dibebankan. `ref_no` dan kunci operasi lokal **belum menjamin idempotensi vendor**: setelah timeout, periksa hasil operasi/rekonsiliasi manual sebelum mengulang POST; kontrak hanya menyediakan lookup berdasarkan AWB, bukan `ref_no` bila AWB belum diketahui. Jika booking manual dipilih, staf tautkan resi ke order lewat SOP. Cetak label hanya setelah jalur label terkonfirmasi dan resi sah; catat serah-terima kurir terpisah. `POST /shipments/cancel` bisa diajukan sebelum pickup namun bisa ditolak.
5. **Monitoring:** terima webhook **Shipment** di URL terpisah dari Omnichannel setelah verifikasi signature menggunakan contoh valid vendor; rekonsiliasi melalui `GET /shipments/awb/{awb}` untuk AWB yang sudah diketahui. Tidak ada endpoint daftar/paginasi shipment di v1.8; rancang polling per AWB tanpa mengasumsikan cursor atau retry webhook terjamin. Simpan event teredaksi dan status ternormalisasi; `tracking.status` kode kurir berbeda dari `latest_status`, hanya `DELIVERED` (atau bukti valid yang disepakati) boleh maju ke completed. Tracking ke pelanggan hanya berdasarkan data provider yang tervalidasi, bukan milestone WMS yang belum tentu delivered. Operasional menangani no pickup, gagal antar/RTO, hilang/rusak, rebooking, refund dan selisih biaya sesuai SOP.
6. **Stock:** jangan secara paralel melakukan adjustment negatif **dan** membuat SO Jubelio yang juga mengurangi stok tanpa membuktikan akibatnya; dokumen migrasi Sales API menjelaskan ketidakpastian ini. Fase awal dapat memisahkan stock ledger yang sudah teruji dari shipment linkage, tetapi pengaruh SO baru terhadap stok wajib dibuktikan di sandbox terlebih dahulu. [Repo: `jubelio-sync.md` §Checkout stock adjustments; `jubelio-sales-api-migration.md` §3–5](jubelio-sales-api-migration.md).

### Batas state yang dianjurkan

- Payment: `pending | paid | failed` (tetap otoritatif Midtrans).
- Order: `pending_payment | processing | failed_payment | cancelled | completed` (status yang kini ada perlu rancangan migrasi khusus; jangan menyalin nama ini mentah tanpa memeriksa seluruh pembaca).
- Fulfillment: `pickup_ready → pickup_verified` **atau** `delivery_awaiting_pack → packed → booking_pending → awb_created → handed_to_courier → in_transit → delivered`, dengan cabang `booking_failed`, `delivery_failed`, `returning/returned`, `manual_review`. Pickup code hanya di jalur pickup; “completed” untuk delivery sesudah bukti penerimaan yang disepakati, bukan setelah pembayaran/print label.

Setiap endpoint yang kelak diimplementasikan perlu dicatat di [`docs/api-reference.md`](../../docs/api-reference.md), log `info` sukses/`error` gagal, tes unit dan E2E sesuai aturan repo; env/cron/webhook baru membutuhkan update `deployment/` dan runbook. Untuk backend request Jubelio baru gunakan safety boundary **non-production mock + live-write kill switch** serupa stock gateway saat ini, bukan otomatis menggunakan kredensial produksi di staging. [Repo: `jubelio-sync.md` §Env; `AGENTS.md` §3–5](../../AGENTS.md).

## 9. Pertanyaan blocker ke Jubelio dan keputusan bisnis

### Verifikasi kontrak/vendor (blocker otomatisasi)

1. Apakah tenant sudah aktif di **Jubelio Shipment** dengan kredensial sandbox dan layanan per cabang? Apakah kontrak v1.8 masih berlaku (terutama path `/rates/all` vs path `/webstore/rates/all` pada plugin, `/shipments/awb/{awb}` vs `/shipments/{shipment_id}`), dan apakah GET kategori/wilayah memerlukan Bearer? Jangan memakai token/ID Omnichannel.
2. Untuk `POST /rates`/`/rates/all`: apa satuan `weight` top-level, aturan volumetrik `items` vs `package_detail`, harga jual yang benar bila ada `rates`/`discount_rates`/`final_rates` (kontrak menyuruh memakai `rates`), arti `shipping_insurance`/COD, jaminan ETA, batas masa berlaku harga, dan penanganan selisih terhadap `price` saat create?
3. Untuk `POST /shipments/create`: bolehkah `ref_no` berisi ID order unik, apakah idempotent, bagaimana mencari shipment sesudah timeout **ketika AWB belum diketahui**, kapan biaya ditagih, dan bagaimana cancel/refund jika pickup hampir terjadi? Bagaimana meminta kurir pickup dan memperoleh **label Shipment** (tidak ada endpoint label di v1.8)? Apakah SO Omnichannel wajib untuk order website, dan bagaimana mencegah potong stok dua kali?
4. Untuk `POST /webhook` dan `GET /shipments/awb/{awb}`: minta fixture signed webhook, klarifikasi SHA-256 biasa vs HMAC-SHA256, raw-body/encoding signature, retry, ordering, daftar event, kode tracking dan status `RETURNED`/`SHIPMENT_ISSUE`; apakah polling per AWB diperbolehkan dan berapa rate limit? Jangan menyamakan callback Shipment dengan `update-salesorder` Omnichannel.
5. Buktikan happy path sandbox untuk **JNE dan sekurangnya satu kurir lain jika tersedia di tenant**, satu asal cabang dan satu order website: token → wilayah → quote → pembayaran → create AWB → GET detail/webhook → delivered, serta cancel, timeout/booking ambigu, selisih harga dan penanganan label (jika didukung). Catat hasil tanpa token atau PII.

### Keputusan produk/operasional (belum diputuskan)

- Pickup **tetap sebagai opsi** atau delivery menggantikan semuanya? Rekomendasi: dual-mode agar pelanggan lama dan cabang yang tidak bisa kirim tetap dilayani.
- Siapa memilih kurir, pelanggan atau admin? Siapa menanggung subsidi gratis ongkir, asuransi, selisih timbang, retry, RTO? Apakah layanan hanya domestik, cabang mana dan SLA berapa?
- Apakah pilot manual masuk akal bila akses tenant Shipment atau verifikasi sandbox belum tersedia? Tentukan harga flat per zona, batas berat, kompensasi selisih, prosedur saat gagal booking dan mekanisme refund sebelum go-live.
- Apakah order lintas cabang tetap ditolak (rekomendasi P0) atau dipecah menjadi beberapa order dan ongkir? Apakah akan ada COD (rekomendasi: **tidak** pada rilis awal karena payment state dan settlement berbeda)?

## 10. Urutan implementasi setelah keputusan diambil, plus verifikasi

1. **Spike vendor (tanpa write produksi):** konfirmasi versi kontrak Shipment v1.8, akses/kredensial sandbox dan uji matriks §3a; uji stok bila SO Omnichannel dipakai. Go/no-go tarif live, booking, webhook dan label **secara terpisah**.
2. **Fondasi data dan UI:** migrasi additive `packages/db/src/schema/`, update seeder FK order; tambah alamat/asal/berat, fulfillment method, status dan snapshot; pickup regression tetap lulus.
3. **Checkout & payment:** `/rates/all` atau `/rates` (gunakan `rates`), snapshot pilihan dan kebijakan umur quote **lokal** atau tarif manual transparan; server authoritative repricing, Midtrans item detail, re-payment dan gagal bayar; uji perubahan alamat, harga berubah, duplicate webhook, voucher/PPN.
4. **Fulfillment admin:** packing → `/shipments/create` → simpan AWB/`shipment_id`/`price`, cancel jika memenuhi syarat; label/serah kurir hanya setelah mekanismenya dibuktikan. Durable operation dan exception queue; permission scope, audit, structured logging; jangan replay POST saat timeout ambigu tanpa rekonsiliasi.
5. **Tracking & rekonsiliasi:** webhook Shipment terverifikasi (algoritma diklarifikasi) + `GET /shipments/awb/{awb}` per AWB yang sudah diketahui; tangani out-of-order, delivered/RTO, notifikasi, selisih biaya, minimisasi PII dan observabilitas SLA.
6. **Uji E2E:** (a) pickup lama → kode → verified; (b) delivery → form wilayah Shipment + alamat tertulis → ongkir → bayar → kemas → AWB → delivered **tanpa pin peta**; (c) alamat tersimpan terpilih otomatis di checkout berikutnya, set-default menyisakan tepat satu default per client; (d) area/kode pos tidak cocok dan alamat pengguna lain ditolak, edit/hapus alamat tidak mengubah snapshot order lama; (e) expired/unpaid tidak booking dan gagal quote tidak checkout; (f) dua worker/duplicate webhook tidak membuat dua shipment; (g) refund/RTO/manual-review; (h) tidak pernah menggandakan potongan stok. `npm run test:unit` untuk logika, Playwright `*.spec.ts` untuk setiap perubahan UI/routing.

**Keputusan paling menentukan:** kontrak Shipment v1.8 kini mendokumentasikan wilayah, kategori, quote, create/cancel AWB, detail tracking dan webhook **di luar** `dist.yaml`; **tidak** mendokumentasikan label, idempotensi, ataupun hubungan Sales Order/stok. Jangan memulai implementasi “pilih JNE dan hitung ongkir otomatis” hanya karena path tertulis: pastikan versi kontrak, aktivasi tenant, harga `rates` vs `price`, keamanan webhook dan bukti sandbox untuk order website. Jika akses tidak tersedia, gunakan pilot manual yang jujur atau provider lain.
